# 内联 Widget：对话内可视化组件（通用版）

> 对应能力：在对话流中渲染紧凑的可视化/交互界面——图表、仪表盘、计算器、滑杆、对比、时间线、状态机、小型模拟。

## 何时用 widget

- 答案具有空间、顺序、系统、对比、数值或交互结构时——"看见结构"比纯文字更助于理解、比较、检查或行动。
- 用户不需要说出"展示/可视化/图表"——结构在那里就主动渲染。
- 用户给出紧凑的视觉规格而无动词（如"REST vs GraphQL 对比表""结账状态机""定价计算器"）→ 直接渲染为 widget，而不只是描述。

**不要用**：普通文字回答、逐行代码讲解、文件列表/画廊/最终交付物、阻塞式输入流程、破坏性操作、大型长驻应用。

## 运行时契约

Widget 运行在消息渲染环境中：

- **允许**：HTML、SVG、CSS、内联 JavaScript、原生浏览器 API。
- **禁止**：外部脚本、模块、样式表、图片、字体、CDN 库、npm 包、`fetch`、WebSocket。图表/图形用 SVG、Canvas、CSS 或纯 DOM 实现。
- **文字在 widget 外，视觉在 widget 内**：解释性文字、引言、总结都写在回复正文里。
- **渲染后不复述**：widget 渲染完成后，不要再总结或重复它表达的内容——视觉自己会说话，只说 widget 表达不了的。
- **回传意图**：交互式 widget 可调用宿主注入的回传接口（如 `window.sendPrompt(text)`）把用户下一步意图推回对话。`text` 要写成真实用户会说的话，而不是机器人式确认（"我选择了选项 A，请继续"）。
- **绝不硬编码颜色、字体、圆角**——尽量引用设计系统的 CSS 变量（`var(--xxx)`）；本系统无全局设计系统时使用内联样式并保持与消息主题协调。

## 设计规范

除非用户对该 widget 给出了非常明确具体的样式指令，否则设计前先遵循良好的视觉设计原则（一致性、对比、留白、可读性）。不要因为 widget"简单/静态/太小"就跳过设计。

图标：优先使用内联 SVG，不要用 emoji 替代（除非主题允许）。
