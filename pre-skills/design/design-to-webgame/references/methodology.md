## 阶段零：环境预检（必须最先完成）

**在动手写任何代码之前**，先检查运行环境，确定技术路线。这一步决定了整个项目的技术栈选择，必须在所有其他阶段之前完成。

### 检查命令

```bash
# 1. 检查 Node.js（必需，没有则只能用纯 HTML）
node --version

# 2. 检查 pnpm（首选包管理器）
pnpm --version

# 3. 如果 pnpm 不可用，检查 npm（备选）
npm --version

# 4. 检查 ComfyUI（可选，美术资源用）
curl -s http://localhost:8188/system_stats || echo "ComfyUI not available"
```

### 技术路线决策树

```
Node.js 可用？
├── 是 → pnpm 可用？
│        ├── 是 → 路线A：React + TypeScript + Vite + pnpm
│        └── 否 → npm 可用？
│                 ├── 是 → 路线B：React + TypeScript + Vite + npm
│                 └── 否 → 路线C：Three.js + ES Modules（无构建）
│                          （如果游戏需要 3D 且 WebGL 可用）
└── 否 → WebGL 可用？
         ├── 是 → 路线C：Three.js + ES Modules（无构建）
         │         适用于 3D 策略/棋牌/环境探索类游戏
         └── 否 → 路线D：纯 HTML + JavaScript + CSS
                   适用于 2D 游戏，零依赖
```

### 路线说明

| 路线 | 技术栈 | 适用场景 | 架构复杂度 |
|:-----|:-------|:---------|:-----------|
| **A** | React + TS + Vite + pnpm | 完整开发环境 | 完整分层架构 |
| **B** | React + TS + Vite + npm | 无 pnpm 但有 npm | 完整分层架构 |
| **C** | Three.js + ES Modules | 无 Node.js，有 WebGL | 3D 模块化架构，无构建 |
| **D** | 纯 HTML + JS + CSS | 无 Node.js，无 WebGL | 简化但保持设计原则 |

### 关键原则

1. **预检结果决定一切**：一旦确定技术路线，整个项目按该路线执行，不要中途切换
2. **提前告知用户**：如果预检发现环境不符合预期（如只能用纯 HTML），应立即告知用户，说明可能的限制
3. **不要写完才发现不行**：这是最常见的错误——先写 React 代码，构建时才发现没有 Node.js

### 环境预检报告模板

检查完成后，向用户报告：

```
环境预检结果：
- Node.js: v18.x.x ✓
- pnpm: 8.x.x ✓
- ComfyUI: 不可用

决定使用路线A：React + TypeScript + Vite + pnpm
美术资源方案：SVG 代码生成
```

### 路线C：Three.js + ES Modules（无构建）补充说明

当 Node.js 不可用但浏览器支持 WebGL 时，使用 Three.js 的 ES Module 模式：
- 下载 three.js 发行版到 `vendor/` 目录
- `index.html` 通过 `<script type="importmap">` 映射本地 three.js
- 所有业务逻辑分散在 `src/` 下的 ES Module 文件中
- `package.json` 只包含开发服务器脚本（`npx serve`），无依赖安装
- 关键技术：程序化建模、`onBeforeCompile` 材质注入、顶点着色器粒子、后处理管线

详见 SKILL.md 中「路线C」章节及 `references/threejs-game-architecture.md`。

## 阶段一：拆解设计文档

通读设计文档，产出一张"系统清单"，每项标注：数值表、触发条件、UI 需求、与其他系统的耦合点。

典型系统清单（经营养成类）：
- 核心循环（做什么动作 → 得到什么 → 解锁什么）
- 制作/战斗等主玩法（含其数值表）
- 经济系统（收入渠道、成本表、定价公式）
- 成长系统（等级、解锁门槛）
- 剧情/养成系统（触发条件、选项效果、结局表）
- UI 布局要求（主界面要显示什么）

落地原则：**文档的每张数值表都应有对应的常量表**；文档的每个"当 X 时触发 Y"都应能在触发检查器中找到一条对应逻辑。

## 阶段二：视觉方向与美术资源

1. **设计参考检索**：用浏览器搜索设计参考，不要凭空决定配色/字体/材质。搜索关键词示例：
   - 英文："pixel game UI"、"retro game interface"、"8bit game palette"
   - 中文："像素游戏界面"、"经营游戏UI"、"复古游戏风格"
   - 具体风格："cyberpunk game UI"、"fantasy RPG interface"、"cute kawaii game"
   
   游戏 UI 特别适合从"复古系统界面"参考中借面板骨架（脊线边框、按压反转按钮、硬阴影）。可配合 `aesthetic-style-library` skill 获取预设风格模板。

2. **中文字体硬约束**：像素/展示字体只管拉丁字母与数字（如 VT323、Press Start 2P），中文必须回退到系统字体栈（PingFang SC / Microsoft YaHei / Noto Sans SC），且禁用 font-style: italic。

3. **美术资源生成策略**（按阶段零的预检结果选择）：
   
   **方案A：本机 ComfyUI**（预检确认可用时）
   - 根据游戏需求自建生图工作流（注意：当前 comfyui-image-gen-workflow skill 针对特定场景，通用游戏美术需要自建工作流）
   - 生成后读图目检：**先 `probe_modality_capability` 确认视觉能力；无视觉（`vision_capable=false`）时不 Read 读图，直接把图片展示给用户判断**
   
   **方案B：SVG 代码生成**（无 ComfyUI 时）
   - 用 SVG 绘制游戏美术：像素风头像、图标、场景背景、UI 元素
   - 优势：完全可控、无外部依赖、可精确匹配游戏风格
   - 工具：可使用 `canvas-design` skill 辅助设计
   
   **方案C：占位图**（极端情况）
   - 纯色块 + 文字标签占位
   - 优先保证游戏可玩性，美术后续迭代补充

4. **全局视觉样式**：面板、按钮、进度条、滚动条集中在一个 CSS 文件，所有界面复用，保证全游戏质感统一。

## 阶段三：代码架构搭建

采用分层架构（详见 architecture.md），搭建顺序根据阶段零确定的技术路线：

### 路线A/B：React + TypeScript

1. `types.ts` —— 先定义 GameState 全字段（这一步强迫你通盘想清楚所有系统的状态形状）
2. `data.ts` —— 把设计文档数值表原样转录为常量
3. `engine.ts` —— 纯函数：定价公式、生成逻辑、判定逻辑
4. `state.tsx` —— reducer，action 与玩家操作一一对应；剧情触发统一收口在一个 checkTriggers 里
5. 场景/对话系统数据化：`Scene` 结构 + 统一播放器 + 队列
6. 界面层最后写，只做"读 state + dispatch"

### 路线C：纯 HTML + JavaScript

1. `js/types.js` —— 常量定义（Object.freeze）
2. `js/data.js` —— 数值表
3. `js/engine.js` —— 纯函数
4. `js/state.js` —— 状态管理（全局 state + pub/sub）
5. `js/scenes.js` —— 场景工厂
6. `js/app.js` —— 主入口、事件绑定、UI 更新

小游戏（QTE 等）做成参数化可复用组件，修正值（buff/debuff）以参数注入。

## 阶段四：数值审校与平衡修正

构建前必须做**量级自洽性检查**：

- 用文档自己的经济节奏描述反推核心数值（如"38 万需 150~200 把"→ 单把收入约 2000G），与文档售价表交叉验证；
- 估算每个阶段需要多少次玩家操作，超过约 50 次重复操作就要警惕可玩性；
- 发现矛盾时：优先引入单一缩放系数只缩放矛盾的子系统，保留其余数值原样；有难度倍率表的照原样实现，缩放系数与难度相乘；
- 生成型内容（顾客、订单）的需求值必须按顾客层级分段，保证低层级的单子用低级产出就能完成（本样例在此出过一个真实 bug：村民订单要求攻击力 111，而初始武器攻击只有 30）；
- **任何偏离设计文档的改动都要主动告知用户并说明理由**。

## 阶段五：浏览器全流程回归

构建通过不等于游戏能玩。启动本地预览服务，用浏览器自动化按真实玩家路径逐步走一遍：

**构建命令**（使用阶段零确定的包管理器）：
- 路线A：`pnpm install && pnpm run build`
- 路线B：`npm install && npm run build`
- 路线C：无需构建，直接打开 HTML 文件

**预览服务**：
- React/Vite 项目：`pnpm run preview` 或 `npx vite preview`（端口避免使用 8765，那是 Gateway 端口）
- 纯 HTML 项目：`python -m http.server <port>` 或直接 `file://` 协议打开

**回归检查清单**：
1. 标题画面（截图目检——**先 `probe_modality_capability`；无视觉则把截图展示给用户目检**）
2. 开场剧情逐行推进、选项生效
3. 主玩法完整跑一轮（材料消耗 → 产出 → 入库 → 数值显示）
4. 每个界面标签页至少打开一次
5. 至少完成一笔完整经济交易（金币、累计值、联动数值全部核对）
6. 社交/养成互动一次（好感变化、资源消耗）
7. 存档回归：刷新页面后读档恢复

每步同时核对 DOM 文本与截图（**截图核对前先 `probe_modality_capability` 确认视觉；无视觉时把截图展示给用户核对**），发现的平衡/交互问题当场修复再回归。

## 阶段六：交付与迭代

**版本管理**（手动管理，不依赖外部服务）：
- 在 `output/` 下按版本号组织目录（如 `output/game-v1.0/`、`output/game-v1.1/`）
- 每个版本保留完整构建产物
- 需要备份时用 `Compress` 工具打包压缩
- 交付说明中注明版本号和变更内容

**存档机制**：
- 单机游戏用 localStorage 存档即可，但**必须明确告诉用户**：存档仅在本浏览器、清缓存丢失、不跨设备
- 如果需要跨设备存档，可考虑导出/导入 JSON 文件的方式

**交付说明**：
- 主动列出：实现了哪些系统、偏离设计的改动及原因、存档机制
- 构建方式和运行方式

**迭代**：优先利用数据驱动层——新对话/新事件 = 新场景工厂函数 + reducer 里一行 pushScene。

## 常见陷阱清单

- **跳过环境预检** —— 先写代码后发现编译不了，浪费大量时间
- 只验证编译通过就交付 —— 必须用浏览器走真实流程
- 数值散落在组件里 —— 改平衡时要满世界找；全部入 data 表
- 剧情触发逻辑散落在各 action 里 —— 收口到统一的触发检查器
- 对话写死在组件 JSX 里 —— 场景数据化，否则后期加对话成本极高
- 中文用纯拉丁像素字体渲染 —— 必须配置中文回退字体栈
- 设计文档数值矛盾悄悄改掉 —— 先交叉验证，改动必须告知用户
- 顾客/订单生成不分层 —— 低级顾客会要玩家造不出的东西
- 忘记告知存档的边界（localStorage 不跨设备）
- 项目中途切换技术路线 —— 预检后确定路线，全程保持一致
